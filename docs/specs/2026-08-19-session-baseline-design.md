# 세션 베이스라인 인프라 설계 (서브프로젝트 B1)

**날짜:** 2026-08-19
**대상:** 연구계획서 목표 3의 서브프로젝트 B 중 첫 조각
**상태:** 설계 승인 완료 → 구현 계획 작성 대기
**선행:** `docs/specs/2026-08-18-simulation-testbed-design.md` (A+D)

---

## 1. 목적

`CLAUDE.md` §3.8이 요구하는 **세션 베이스라인 정규화**를 파이프라인에 넣고,
그것이 실제로 작동한다는 것을 합성 데이터의 ground truth로 증명한다.

목표 4가 학습자·교수자에게 **세션 간 변화**를 보인다. 세션 간 비교 가능성을
파이프라인이 보장하지 않으면, 장비 재부착으로 생긴 측정 드리프트가 인지 변화로
표시된다. 학습자는 나아지지 않았는데 나아졌다고 듣는다.

이 스펙이 증명해야 하는 명제는 두 개이고, **둘째가 첫째보다 중요하다.**

1. 정규화가 측정 드리프트를 지운다
2. **그러면서 진짜 인지 변화는 지우지 않는다**

1만 증명하면 "세션 간 모든 차이를 없애는 함수"도 통과한다. 그런 함수는 종단
프로필을 영원히 평평하게 만든다.

## 2. B의 분해와 이 문서의 위치

서브프로젝트 B(전처리)는 단일 스펙 범위를 넘는다. 척추 우선 3분할한다.

| | 조각 | 내용 | 상태 |
|---|---|---|---|
| **B1** | 세션 인프라 | 베이스라인 블록 · 세션 축 · 드리프트 모사 · 계약 확장 · 세션 베이스라인 정규화 | **이 문서** |
| **B2** | fNIRS 신호 체인 | 원시 광강도 · 진입 수준 · SCI · `coupling_quality` · 웨이블릿 · mBLL · 광량/모션 아티팩트 | 미착수 |
| **B3** | EEG 신호 체인 | PREP · 필터 · ASR · 불량채널 보간 · 눈깜빡임/EMG 아티팩트 | 미착수 |

### B1을 먼저 하는 이유

B1은 **혼자서 완결된다.** fNIRS 진입 수준을 "농도"로 잡으면 신호 체인 없이도
`세션 드리프트 → 분류 붕괴 → 정규화 → 회복 + 학습효과 생존` 전체를 증명할 수
있다. 특징은 A+D의 임시 추출기(`features_minimal`)를, 분류기는 더미 로지스틱
회귀를 그대로 쓴다.

척추가 먼저 서 있으면 B2에서 결과가 이상할 때 원인이 **신호 체인인지 세션
처리인지 분리된다.** 반대 순서로는 분리할 수 없다.

## 5. 데이터 모델

### 5.1 심는 위치가 다르다 — 설계의 축

| 변동원 | 어디에 심는가 | 정규화 |
|---|---|---|
| ① 옵토드 재부착 · ② 캡/임피던스 · ③ 세션 내 드리프트 | **신호 변환** — 인지상태는 그대로인데 관측만 왜곡 | 지워야 함 |
| ④ 연습 효과 | **인지상태 자체** — `CognitiveStateTimeline`이 실제로 바뀜 | 살려야 함 |

①②③은 `signal = f(state)`의 `f`를 흔들고, ④는 `state`를 바꾼다. 층이 다르므로
"정규화는 ①②③만 지우고 ④는 남긴다"가 **원리적으로 성립하는 요구**이지 튜닝으로
맞추는 목표가 아니다. §8의 승인기준이 이 구조에 기댄다.

### 5.2 세션 구조

```
세션 = [BASELINE_시작] + [TASK 블록 × N] + [BASELINE_종료]
피험자당 n_sessions회 (기본 3, config)
```

`CognitiveStateTimeline`에 두 필드를 추가한다.

- `block_kind: np.ndarray` — 블록별 `BASELINE` / `TASK`
- `session_idx: int` — 0-based 세션 번호

기본 3세션인 이유: CLAUDE.md §3.8이 3회 미만에서 추세선을 금지한다. 연습 효과 회귀
기울기를 추정하려면 최소 3점이 필요하다.

베이스라인 블록 길이는 config(`baseline_duration_s`). 과제 블록과 달리 자극이
없으므로 `stim_onsets`를 생성하지 않는다.

### 5.3 드리프트 모델

세션 `s`, 채널 `c`에 대해 `session.py`가 파라미터를 뽑고
`components/drift.py`가 깨끗한 신호에 적용한다. 기존 성분 플러그인은 손대지
않는다 — 그들은 계속 깨끗한 신호를 만들고, 드리프트는 그 뒤에 곱해진다.

**① fNIRS 옵토드 재부착**

```
gain[s,c]   ~ LogNormal(0, sigma_gain)
offset[s,c] ~ Normal(0, sigma_offset)
y = gain * x + offset
```

**곱셈 이득이 핵심이다.** 광 결합도는 곱셈적이라, 가산 오프셋만 심으면 정규화
난이도가 비현실적으로 쉬워진다(평균 빼기로 끝난다).

**② EEG 캡 위치·임피던스**

```
gain[s,c]        ~ LogNormal(0, sigma_gain_eeg)
noise_scale[s,c] ~ LogNormal(0, sigma_noise_eeg)
```

DC 오프셋은 넣지 않는다 — 어차피 대역통과로 죽으므로 모사해도 아무것도 시험하지
못한다. 임피던스 상승의 본질은 진폭 변화가 아니라 **잡음 증가**이므로
`noise_scale`을 둔다.

**세션 0도 자기 드리프트를 갖는다.** "무드리프트 기준 세션"을 두면 실제와 다르고,
정규화 테스트가 부당하게 쉬워진다.

**③ 세션 내 드리프트**

```
gain(t) = gain[s,c] * (1 + rate[s] * t / T)
```

`rate[s]`는 세션마다 다르게 뽑되 **일부 세션에만 크게** 뽑는다(config로 큰
드리프트 세션의 비율을 지정). 전부 균일하면 신뢰도 플래그가 판별력을 가질 수
없다 — 전부 플래그되거나 전부 안 되거나이므로 §8 T6이 무의미해진다.

### 5.4 연습 효과 (④)

`state.py`에서 심는다. 동일 n-back 수준의 인지부하가 세션마다 감소한다.

```
effective_load = load_fraction(level) * (1 - practice_rate) ** session_idx
```

기하 감쇠를 쓴다. 선형 감소(`1 - rate * session_idx`)는 `n_sessions`가 커지면
음수가 되어 인지부하가 뒤집힌다 — `n_sessions`가 config인 이상 그 조합이 실제로
들어올 수 있다. 기하 감쇠는 단조 감소이면서 항상 양수다.

신호 쪽은 전혀 손대지 않는다. 이것이 5.1의 층 분리를 코드로 구현한 지점이다.

감쇠의 **형태**는 모델링 가정이다. 실제 연습 효과는 천장 효과나 다른 곡선일 수
있으며 실데이터로만 확인할 수 있다. §12 참조.

### 5.5 난수열 규율

`SubjectProfile`의 τ² 교훈(`src/simulation/subject.py` 주석)을 그대로 지킨다.

> **드리프트 크기가 0이어도 분기하지 않고 항상 `rng`를 소모한다.**

`np.zeros`로 우회하면 "드리프트 없음" 조건이 다른 난수열 위에서 돌아, 블록
순서도 잡음도 달라진다. 그러면 §8 T2의 결함 주입("드리프트를 끄면 붕괴가
사라진다")이 단일 변수 조작이 아니게 된다.

## 6. 정규화 계층

### 6.1 `SessionBaseline` — 구조로 강제하는 경계

```python
class SessionBaseline:
    @classmethod
    def fit(cls, start_baseline, kind) -> SessionBaseline: ...
    def apply(self, x) -> np.ndarray: ...            # kind는 fit에서 고정된다

def compute_drift(start_baseline, end_baseline, *, zero_atol) -> SessionDrift: ...
```

`kind`는 `fit`에서 한 번만 받는다. `apply`가 다시 받으면 fit과 다른 `kind`를 넘길
수 있게 되고, 그건 의미 있는 사용처가 없으면서 조용히 틀릴 수 있는 경로다.

드리프트는 두 베이스라인을 모두 봐야 하므로 `SessionBaseline`의 메서드가 아니라
별도 함수다 — `fit`이 시작 베이스라인만 받는다는 §6.1의 요점을 지키기 위함이다.

**`fit`은 한 세션의 베이스라인 에포크만 받는다.** 다른 세션·다른 피험자를 넘길
인자가 존재하지 않는다. `TestView.fit()`이 무조건 예외를 던지는 것과 같은 발상 —
규율이 아니라 서명으로 막는다.

### 6.2 `kind`별 규칙

| kind | 대상 | 처리 |
|---|---|---|
| `concentration_delta` | fNIRS HbO/HbR | 시작 베이스라인의 **평균과 산포**를 기준으로 고정: `(x - 베이스라인 평균) / 베이스라인 표준편차(ddof=1)` |
| `band_power_db` | EEG 대역 파워 | 시작 베이스라인 대비 dB. 절대 µV²는 세션 간 비교에 쓰지 않음 |
| `absolute` | 행동 (정오답률·반응시간) | **변환하지 않음.** 장비 재부착의 영향을 받지 않으므로 |

기준은 **시작 베이스라인만** 쓴다. 종료 베이스라인은 정규화에 쓰지 않고 드리프트
추정에만 쓴다. CLAUDE.md §3.8에서 확정된 사항이므로 재론하지 않는다.

`absolute`가 무변환이라고 해서 생략 가능한 것은 아니다. 명시적 `kind`를 요구해서
"행동에 어떤 정규화를 적용할지 생각하지 않고 넘어가는" 경로를 막는다.

**2026-08-19 정정 (Task 14/B1, T3에서 발견) — `concentration_delta`가 뺄셈만
하던 원안은 부족했다.** 옵토드 재부착의 지배적 효과는 결합도·유효 광경로
변화이며 이는 **곱셈적**이다(`y = gain·x + offset`). 뺄셈(`x - 베이스라인 평균`)은
`offset`만 지우고 세션마다 다른 `gain`은 남긴다:

```
y - mean(y_base) = gain·(x - mean(x_base))     ← 이득이 여전히 남는다
```

반면 EEG의 `band_power_db`는 **비율**(`10·log10(y/mean(y_base))`)이라 `gain`이
분자·분모에서 자동으로 상쇄된다 — 두 모달리티가 애초에 비대칭이었다. Task 14의
T3(회복) 검증에서 이 비대칭이 실측으로 드러났다: 회복률이 0.268(요구 ≥0.5)에
그쳤고, `fnirs_gain_sigma=0`으로 두면(다른 드리프트는 유지) 회복률이 0.378로
오르는 것으로 원인이 확인됐다.

고친 식은 베이스라인 **산포**로도 나눈다:

```
(y - mean(y_base)) / std(y_base)
    = (gain·x + offset - (gain·mean(x_base) + offset)) / (gain·std(x_base))
    = (x - mean(x_base)) / std(x_base)      ← gain이 분자·분모에서 상쇄
```

수정 후 결과 단위는 **베이스라인 산포 대비 배수**(무차원)로 바뀐다. 분모가
**베이스라인 블록**(과제 반응이 없는 안정 상태)의 산포이지 세션 전체의 산포가
아니므로, 과제 반응의 크기(연습 효과가 만드는 신호 변화)는 분자에 그대로
보존된다 — "세션 전체 z-score"와 다른 지점이며, Task 15(T4, 기울기 보존율)가
정확히 이 성질을 검증한다. σ≈0인 채널은 `_SCALE_FLOOR`(1e-8)로 하한 처리해
발산을 막는다. 구현: `src/preprocessing/baseline.py`의 `SessionBaseline` 클래스
docstring 참조.

수정 후 T3 재실측: 회복률 0.268 → **0.335**로 개선됐으나 여전히 0.5 미달이다.
잔여 격차의 원인을 추적한 결과, 드리프트를 전부 0으로 둬도(`fnirs_gain_sigma
=fnirs_offset_sigma=eeg_gain_sigma=eeg_noise_sigma=within_session_rate=0`)
cross_session 정확도가 0.5112로 within_subject 상한(0.8586)에 크게 못 미쳐
같은 회복률(0.339)이 나온다 — 즉 **잔여 격차의 대부분은 드리프트나 정규화
문제가 아니라, `cross_session`(피험자 내·세션 간 일반화)과 `within_subject`
(세션 내 일반화)의 근본적인 난이도 차이다.** `cross_session`은 fold 3개(세션
수)뿐이고 학습에 쓸 수 있는 세션이 2개뿐인 반면 `within_subject`는 같은
세션 안에서 블록만 나누므로 원리적으로 훨씬 쉽다. 이는 정규화로 고칠 수 있는
문제가 아니다. 상세: `run_logging.md`,
`.superpowers/sdd/2026-08-19-session-baseline/task-14-report.md`.

### 6.3 신뢰도 플래그

**2026-08-19 정정 (최종 리뷰 — 본문이 정정 이력을 못 따라잡고 있었다).** 아래는
현재 구현(`src/preprocessing/baseline.py::compute_drift`)이다. 초판 수식(`||end −
start|| / ||start||`, 채널별 **크기**가 0에 가까우면 배제)은 fnirs 특징이 `[HbO
평균 | HbO 기울기]`를 이어붙이고 "기울기" 채널은 베이스라인(고정점 응시, 추세
없음)에서 평균이 정당하게 0 근처라는 사실과 충돌해 비율이 발산했다(§8.4.1 "정정
6" 참조). 분모를 **산포**로 바꿔 고쳤다:

```
per_channel   = |mean(end_baseline) - mean(start_baseline)| / std(start_baseline, ddof=1)
                (채널별)
aggregate     = per_channel[유효 채널].mean()
drift_flag    = aggregate > drift_threshold_relative  (또는 유효 채널이 하나도 없으면 nan → 플래그)
```

드리프트는 **정규화 전 원 단위**에서 계산한다. dB 변환 후에는 기준값이 정의상 0이
되어 상대 비율이 성립하지 않는다. 베이스라인 **산포**(`std(start, ddof=1)`)가
`zero_atol` 이하인 채널은 비율이 발산하므로 집계에서 제외하고 **불량 채널로 따로
보고**한다(`n_excluded`) — 조용히 버리면 "드리프트 없음"으로 오독된다. 배제 기준이
"크기가 0"이 아니라 "산포가 0"인 이유: 위에서 본 기울기 채널처럼 평균(크기)이
정당하게 0인 채널도 있어, 크기를 기준으로 배제하면 그 채널들을 통째로 놓친다.

`SessionQuality(drift_flag, session_drift, ...)`는 **에포크 → 데이터셋까지는
따라가지 않는다.** `build_dataset`(러너)이 `WindowedDataset`과 별도로
`list[SessionQuality]`를 반환하고, `WindowedDataset` 자체는 품질 필드를 싣지
않는다 — 전파 경로는 **녹화 → 러너 → `session_quality.csv`**에서 끝난다.
대시보드(목표 4, 아직 미착수)로 이어지려면 별도 배선이 필요하다. CLAUDE.md
§3.8대로 값을 감추지 않고 불확실성과 함께 보인다는 원칙 자체는 유지되지만, 현재
그 원칙이 실제로 닿는 범위는 `session_quality.csv`까지다. 임계는 config이며,
CLAUDE.md §3.5의 "교수자가 임계치 조정 가능"과 같은 성질이다.

### 6.4 누수 논증과 가드

이 부분은 리뷰에서 반드시 공격받으므로 명시적으로 적는다.

**논증(조건부다 — 조건을 먼저 적는다):** 베이스라인 블록은 과제 조건이 없어
인지부하 라벨이 없고, 따라서 **부하 타깃에서는** 분류 데이터셋에서 배제된다. 그
경우 정규화 파라미터의 출처는 train도 test도 아닌 데이터이며, 라벨 정보가
건너가지 않고 다른 피험자·다른 세션 통계를 참조하지 않는다.

**이 논증은 무조건 참이 아니다.** §6.5가 베이스라인 윈도우를 타깃별 옵트인으로
남겨두므로, 피로처럼 베이스라인을 분석에 넣는 타깃에서는 "train도 test도 아니다"가
성립하지 않는다. 그 타깃은 **다른 정규화 기준을 명시적으로 선택해야 한다.**

논문·보고서에 이 논증을 옮길 때는 **"부하 타깃에 대하여"라는 한정을 반드시 함께
옮긴다.** 한정을 떼면 부정확한 진술이 된다.

**"test 세션의 자기 베이스라인을 쓰는 것은 test 데이터 사용 아닌가"에 대한 답:**
비지도이고, 세션 내부에 갇혀 있고, **배치 시점에도 실제로 확보 가능**하다
(프로토콜이 매 세션 베이스라인을 의무화했으므로). 전체 데이터에
`StandardScaler`를 fit하는 것과는 다른 부류다. 이미지별 평균 빼기에 가깝다.

**가정에 기대지 않고 가드로 강제한다:**

> 데이터셋이 `normalization_source_mask`를 싣는다 — 베이스라인 fit에 쓰인
> 윈도우의 표식. 표식된 윈도우가 train 또는 test에 나타나면 `LeakageError`.

이로써 "베이스라인은 train도 test도 아니다"가 설계상의 사실에서 **가드가 지키는
불변식**으로 승격된다.

### 6.5 베이스라인 윈도우는 삭제하지 않는다

베이스라인 윈도우를 윈도잉 단계에서 버리지 않는다. `block_kind=BASELINE`으로
태깅해 데이터셋에 남기고, **인지부하 타깃의 라벨 빌더가** 배제한다.

배제하는 세 이유(강한 순서로):

1. **자기 자신으로 정규화한 표본은 퇴화한다.** 베이스라인 구간의 평균이 곧
   기준값이므로 정규화 후 베이스라인 윈도우는 구조적으로 0 근처가 된다. 분석에
   넣으면 완벽히 분리되는 클래스가 공짜로 생기고 정확도가 오른다 — 신호가 아니라
   정규화 정의 때문에.
2. **chance level이 조용히 바뀐다.** 3수준 분류(chance 33.3%)가 4클래스(25%)가
   된다. 게다가 CLAUDE.md §9.2 4번 "3수준 분류"의 정의가 아직 미확정이다. 베이스라인을
   클래스로 넣는 것은 미확정 스펙을 코드로 확정하는 일이다(CLAUDE.md §10).
3. **드리프트 지표가 순환한다.** `session_drift`는 베이스라인 블록에서 계산된다.
   그 블록이 분석 데이터이기도 하면 신뢰도 플래그와 플래그 대상이 같은 숫자다.

**대가:** 피로(CLAUDE.md §2.1 `fatigue`)는 베이스라인에서 가장 깨끗하게 측정된다. 과제
수행 중에는 난이도와 섞이지만 안정 상태에서는 섞이지 않는다. 휴식 vs 과제 대비도
정당한 연구 질문이다. 그래서 삭제가 아니라 **옵트인**으로 둔다. 옵트인 시 1번
문제가 되살아나지만, §6.4의 가드가 먼저 터져서 "이 타깃에서는 다른 정규화 기준을
쓰겠다"를 명시적으로 결정하게 만든다. 조용히 통과하지 않는다.

## 7. 계약·분할기 변경

### 7.1 현재 코드의 결함 2개

세션 축이 들어가면 기존 코드 두 곳이 **조용히 틀린다.** A+D 시점에는 존재할 수
없던 결함이다 — 세션이 없었으므로.

**결함 1 — `trial_id` 충돌.** `src/simulation/state.py`의 `trial_id`는 녹화마다
0부터 센다. 세션이 여럿이면 `sub-01`의 세션0-블록3과 세션1-블록3이 같은
`trial_id`를 갖는다. `WithinSubjectSplitter`는 trial로 나누므로 두 세션의 블록이
한 덩어리로 묶이고, 시행이 더 이상 일관된 단위가 아니게 된다.

→ **`trial_id`를 데이터셋 전역 고유로** 만들고 `session_ids`를 별도로 싣는다.

**결함 2 — `check_window_overlap` 오탐.** `src/evaluation/guards.py`는 같은
피험자 안에서 창 시각이 겹치면 실패시킨다. 그런데 `window_times`도 세션마다 0부터
다시 센다. 세션이 다르면 물리적으로 다른 녹화인데 시각이 같다는 이유로 누수로
판정된다 — **`CrossSessionSplitter`가 아예 돌지 못한다.**

→ 비교 단위를 `(subject, session)`으로 바꾼다.

### 7.2 `SplitKeys`

```python
@dataclass(frozen=True)
class SplitKeys:
    subject_ids: np.ndarray
    session_ids: np.ndarray
    trial_ids: np.ndarray
    labels: np.ndarray | None
```

`Splitter.split(keys: SplitKeys)`로 서명을 바꾼다. 위치 인자를 하나 더 붙이지
않는 이유는, 다음에 축이 또 생기면(run, 과제 유형) 같은 파손을 반복하기
때문이다. 기존 분할기 3개·하네스·해당 테스트가 함께 바뀐다.

### 7.3 분할기 표

`allows_same_subject` 옆에 **`allows_same_session`**을 추가하고 가드를 하나 더
건다.

| 분할기 | `allows_same_subject` | `allows_same_session` | 용도 |
|---|---|---|---|
| `LosoSplitter` | ✗ | ✗ | 교차 피험자 일반화 |
| `WithinSubjectSplitter` | ✓ | **✓** | 세션 내 성능 |
| **`CrossSessionSplitter`** (신규) | ✓ | ✗ | 세션 간 비교 (CLAUDE.md §3.8 종단 프로필) |
| `WindowRandomSplitter` | ✗ | ✗ | 누수 시연 전용 |

**세션 중첩 검사는 `(피험자, 세션번호)` 복합 키로 한다.** `session_idx`만 보면
피험자 A의 세션 0과 피험자 B의 세션 0이 같은 세션으로 취급되어 LOSO가 자기 자신의
가드에 걸린다. `session_idx`를 int로 싣는 이유는 `CrossSessionSplitter`가 피험자를
가로질러 같은 번호의 세션을 묶어야 하기 때문이며, 복합은 가드가 수행한다.

`allows_same_subject`와 마찬가지로 **속성을 생략하면 `False`로 간주**한다. 새
분할기를 쓰는 사람이 아무것도 선언하지 않으면 가장 엄격한 쪽으로 떨어진다.

`WithinSubjectSplitter`는 **세션 안에서만** 시행을 나눈다 — 그래서 같은 세션이
train과 test 양쪽에 나타나며 `allows_same_session=True`다. 세션을 가로질러 나누면
세션 간 성능을 세션 내 성능으로 잘못 보고하게 된다(CLAUDE.md §5.4 위반). 그룹 키가
`(피험자)`에서 `(피험자, 세션)`으로 바뀐다.

### 7.4 `cv_scheme` 분리

`CrossSessionSplitter` 결과는 CLAUDE.md §5.4에 따라 **LOSO와 같은 표에 섞지 않는다.**

- 하네스가 결과에 `cv_scheme`(`loso` / `within_subject` / `cross_session`)을 기록
- 러너의 집계가 서로 다른 `cv_scheme`을 합치려 하면 거부

## 8. 승인기준

A+D 표준을 그대로 적용한다 — **각 테스트는 대상 결함을 주입했을 때 실제로
빨개지는 것을 함께 보인다.** 실패할 수 없는 테스트는 테스트가 아니다.

| | 조건 | 기대 | 결함 주입 |
|---|---|---|---|
| **T1 널** | `effect_size=0`, 드리프트 on | 세션 간·LOSO 모두 chance가 CI 안. **정규화 전후 모두** | §8.1의 두 가지 (부하 조건부 정규화 / 부하 의존 드리프트) |
| **T2 붕괴** | 효과 on, 드리프트 on, **정규화 off** | 세션 간 정확도가 chance 근처로 붕괴 | 드리프트를 끄면 붕괴가 사라져야 함 |
| **T3 회복** | 동일 데이터, **정규화 on** | **드리프트 비활성 `cross_session`**(같은 분할기·같은 시드, 시그마만 0) 수준 근처로 회복 — ~~세션 내(`within_subject`) 수준~~(2026-08-19 정정: §8.4.1 참조, `within_subject`는 답하는 질문이 달라 상한이 될 수 없다) | 정규화 기준을 **다른 세션** 베이스라인으로 바꾸면 회복 실패 |
| **T4 음성대조** | 정규화 on | 심어둔 **연습 효과 생존** — §8.2의 기울기 보존율이 하한 이상 | 정규화를 "세션별 전체 z-score"(과한 정규화)로 바꾸면 보존율이 0으로 죽어야 함 |
| **T5 누수** | — | `normalization_source_mask` 윈도우가 fold에 들어오면 `LeakageError`. `SessionBaseline.fit`에 타 세션 주입 시도 실패 | 가드를 지우면 통과해버려야 함 |
| **T6 신뢰도** | §8.3의 2×2 배치 | ③이 큰 세션만 플래그. **①②가 커도 ③이 작으면 플래그되지 않을 것** | ~~임계를 0으로 낮추면 전부 플래그되어 특이도가 무너져야 함~~ (2026-08-19 정정: 이 주입은 폐기됐다 — 드리프트가 정확히 0이 아닌 한 임계 0에서는 거의 항진명제였다. 대신 `compute_drift`가 종료 베이스라인을 못 보게 만드는 주입으로 교체: 양성 칸(세션1·3)의 플래그율이 100%→0%로 무너져야 함. §8.4.1 "정정 8" 참조) |

**T2와 T3는 쌍이다.** T3만 있으면 "정규화하니 잘 되네"이고, T2가 있어야 "정규화가
*무엇을* 고쳤는지"가 된다. T3의 존재 이유가 T2다.

**T4가 이 서브프로젝트의 존재 이유다.** T2·T3만이면 §1의 명제 1만 증명한 것이고,
T4가 명제 2를 맡는다. 목표 4의 종단 프로필이 여기에 걸려 있다.

### 8.1 T1은 무엇을 잡는가 — 결함 주입을 명시한다

초안에서 T1의 결함 주입 칸이 비어 있었다. 우리 기준으로 그 자체가 경고다. 실제로
T1은 그냥 두면 **거의 자동으로 통과한다** — 드리프트는 세션별 채널 이득인데 부하
수준은 세션 *안에서* 무작위 배치되므로, 드리프트가 부하를 예측할 원리적 경로가
없다.

그래도 T1이 잡는 것이 있다. 둘 다 실제로 일어날 수 있는 구현 버그다.

**주입 1 — 부하 조건부 정규화.** 정규화를 세션 단위가 아니라 `(세션 × 부하수준)`
단위로 중심화하도록 바꾼다. 그러면 잔차에 부하가 인코딩되어 `effect_size=0`인데도
정확도가 chance를 넘는다. T1이 빨개져야 한다.
— 이것은 가상의 실수가 아니다. "그룹별로 정규화하면 더 깨끗하다"는 유혹은 흔하고,
`groupby` 키를 하나 더 넣는 것만으로 발생한다.

**2026-08-19 정정 (최종 리뷰) — 위 서술대로 구현하면 T1이 통과해버린다. 실제
주입은 다른 결함이다.** 브리프 원안(세션 자신의 `(세션×부하수준)` 그룹 평균으로
센터링해 0으로 만드는 버전)을 실제로 돌려보니 fold_ci를 못 깼다 — `effect_size=0`
이면 애초에 그룹 간 차이가 없으므로 "자기 평균을 빼서 0으로 만드는" 연산은
정보를 지우기만 할 뿐 새로 주입하지 않는다(`pooled_ci`조차 chance를 포함: mean
0.335, pooled_ci [0.319, 0.350]).

구현(`tests/evaluation/test_validation_session.py::test_t1_injection_1_load_conditional_normalization_breaks_the_null`)
은 **훨씬 노골적인 결함으로 교체됐다**: **train/test 구분 없이 전체 데이터셋(테스트
fold 포함)에서 부하수준별 평균을 먼저 계산해두고, 그 전역 평균을 모든 세션에
동일하게 주입**한다. 이러면 잔차가 세션마다 우연히 같은 상수 벡터를 공유하게 돼
분류기가 그 벡터로 즉시 학습한다 — CLAUDE.md §5.1이 경고하는 "전체 데이터에 fit"
누수의 정석적인 형태이며, 실측 `accuracy_mean=0.475`, `fold_ci_low=0.453`
(chance 0.333)로 명확히 깬다.

**따라서 T1은 이 절이 원래 겨냥한다고 선언한 버그("그룹별 정규화를 세션 자신의
평균으로 하되 실수로 그룹 키를 하나 더 넣는 것")를 잡지 못한다** — 그 버전은
정보를 지우기만 하고 chance를 넘기지 못했다. T1이 실제로 잡는 것은 그보다 심한
전역-fit 누수뿐이다.

**추가 주의.** 이 교체된 주입은 `runner_mod.get_extractor`를 몽키패치해 특징
추출기 자체를 바꿔치기하는 방식으로 구현된다 — `src/preprocessing/baseline.py`의
`SessionBaseline`/`compute_drift` 경로는 건드리지 않는다. 즉 **T1이 통과한다는
사실은 `baseline.py`의 정규화 코드에 이런 결함이 없다는 증거가 아니다** — T1이
검증하는 것은 "이런 형태의 전역-fit 누수가 있으면 fold_ci가 chance를 벗어난다"는
지표 감도뿐이고, `baseline.py`가 실제로 이 결함에서 자유로운지는 별도로
확인해야 한다.

**주입 2 — 부하 의존 드리프트.** `components/drift.py`가 블록마다 `rng`를
소모하도록(즉 드리프트 파라미터가 부하 조건 배열에 의존하도록) 바꾼다. 그러면
드리프트 자체가 부하의 대리변수가 되어 chance를 넘는다. T1이 빨개져야 한다.
— 이것도 실수하기 쉽다. 세션 단위로 한 번 뽑아야 할 것을 루프 안에서 뽑으면 된다.

두 주입 모두 통과해버리면 T1은 삭제한다. 실패할 수 없는 테스트를 승인기준에
남겨두지 않는다.

### 8.2 T4의 측정 방법 — 기울기 보존율

"심은 값 부근"은 절대 수치를 요구하므로 쓰지 않는다. 대신 **같은 회귀를 두 번
돌려 비율을 본다.** 무엇을 회귀하는지가 중요하므로 명시한다.

**분류기 출력은 쓰지 않는다.** 두 가지 이유로 틀린 측정이 된다.
(a) 분류기 출력은 클래스 인덱스 단위이고 ground truth는 부하 비율 단위라 비율의
분모·분자가 서로 다른 척도다. (b) 더 나쁘게는, **잘 작동하는 분류기일수록 약해진
신호를 여전히 올바른 클래스로 되돌리므로 추정 부하가 감소하지 않는다** — 정규화가
정상인데도 T4가 실패한다.

**대신 정규화된 특징을 직접 회귀한다.**

고정된 n-back 수준 L에 대해, `m(s)` = 세션 `s`의 수준 L 창들에서 구한 **정규화된
fNIRS HbO 평균 특징**의 평균(피험자 전체 풀링). `m(s) = a + b·s`를 적합한다.

| 기울기 | 어느 실행에서 |
|---|---|
| `b_hat` | 드리프트 **on** + 정규화 **on** — 실제 파이프라인 |
| `b_ref` | 드리프트 **off** + 정규화 **off** — 연습 효과만 남은 깨끗한 신호 |

> **2026-08-19 정정 (Task 15, §8.4.1 "정정 3" 참조):** 아래 표는 §6.2가
> `concentration_delta`를 뺄셈만 하던 시점의 정의다. 베이스라인 산포로도 나누게
> 정정되면서 `normalize=True`의 결과 단위가 바뀌어, `b_ref`를 `normalize=False`로
> 구하면 `b_hat`(`normalize=True`)과 단위가 달라져 비율이 발산한다(실측 72.07).
> **구현은 `b_ref`도 `normalize=True`로 계산한다** — 드리프트만 끄고 정규화
> 파이프라인은 `b_hat`과 동일하게 태운다. 실측값·근거는 §8.4.1 정정 3.

**보존율 = `b_hat / b_ref`**

두 값이 **같은 특징·같은 단위**이므로 비율이 의미를 갖는다. `b_ref`는 우리가 심은
연습 효과가 특징에 실제로 나타나는 크기이며, 드리프트가 없으므로 정규화도 필요
없다. 보존율이 1 근처면 연습 효과가 온전히 살아남은 것이고, 0 근처면 정규화가
지운 것이다.

두 실행은 **같은 시드**를 쓰므로 §5.5의 난수열 규율이 여기서 값을 한다 — 드리프트를
꺼도 다른 난수열로 넘어가지 않아야 `b_ref`가 `b_hat`의 정당한 기준이 된다.

보존율의 **하한**은 파일럿 보정 대상이다(§8.4). 상한도 둔다 — 보존율이 1을 크게
넘으면 정규화가 없던 변화를 만들어낸 것이므로 그것도 실패다.

**2026-08-19 참고 (T3 상한 정정과의 관계):** `b_ref`가 여기서도 "같은 파이프라인,
드리프트만 끔"(`within_subject`처럼 **다른 분할기**로 바꾸는 게 아니다)이라는
점이 중요하다. T3의 최초 상한 정의(§8.4.1)가 `within_subject`를 썼다가 실패한
이유가 바로 "다른 CV 방식으로 바꿔 비교"였다 — `within_subject`는 세션 간 이동을
아예 겪지 않으므로 드리프트가 없어도 `cross_session`보다 훨씬 쉽다. `b_ref`가
처음부터 이 실수를 피한 것은, "정규화 대상은 드리프트뿐이고 분할 방식이 만드는
난이도 차이는 별개"라는 원칙을 지켰기 때문이다 — T3도 같은 원칙으로 다시 썼다.

### 8.3 T6의 음성 사례 — 무엇이 플래그되지 *않아야* 하는가

민감도만 보면 T6은 순환이다. ③이 곧 세션 내 이득 드리프트이고 `drift_flag`는
시작↔종료 베이스라인 차이로 계산하므로, **심은 것을 그대로 재는 셈**이라 검출은
거의 보장된다.

실제로 묻는 것은 **특이도**다. `drift_flag`는 "이 세션의 종단 비교값을 믿지 말라"는
신호인데, 세션 *간* 드리프트(①②)는 정규화가 이미 처리하므로 플래그 사유가 아니다.
①②가 큰 세션까지 플래그하면 경고가 남발되고 아무도 안 본다.

그래서 세션을 2×2로 배치한다.

| | ③ 세션 내 드리프트 작음 | ③ 큼 |
|---|---|---|
| **①② 세션 간 드리프트 작음** | 플래그 ✗ | 플래그 ✓ |
| **①② 큼** | **플래그 ✗ ← 핵심 칸** | 플래그 ✓ |

왼쪽 아래 칸이 T6의 존재 이유다. 여기가 플래그되면 `drift_flag`가 세션 간
드리프트를 세션 내 드리프트로 오독하고 있다는 뜻이고, 그건 §6.3의 정의가 잘못
구현된 것이다.

**T6은 전용 검증 config를 쓴다.** 일반 생성기는 ①②③을 분포에서 뽑으므로 2×2가
우연에 맡겨진다. T6 config는 세션별 드리프트 크기를 **결정적으로 배정**한다
(`drift.assignment: fixed_2x2`). 이는 A+D의 T1~T4가 각자 전용 config를 쓴 것과
같은 방식이다.

### 8.4 임계치는 이 스펙에 박지 않는다

T2·T3의 회복 폭, T6의 드리프트 임계, T4의 기울기 허용 범위는 **숫자를 지금 정하지
않는다.** 구현 중 파일럿 측정 후 근거와 함께 고정하고, 그 근거를 `run_logging.md`에
기록한다.

A+D의 T3에서 근거 없이 "15pp 향상"을 적어놨다가 실측 7.55pp를 만나 재보정한 일이
있다. 사전에 숫자를 지어내면 나중에 그 숫자를 맞추려는 압력이 생긴다.

### 8.4.1 파일럿 관측 (session_recovery.yaml, seed 42)

**정정 1 — concentration_delta 정규화 (§6.2, 뺄셈만 → 뺄셈+베이스라인 산포로 나눔):**

| 조건 | pooled accuracy (정정 전) | pooled accuracy (정정 후) | fold CI (정정 후) |
|---|---|---|---|
| cross_session · 정규화 off | 0.4126 | 0.4126 (불변 — off는 정규화 미사용) | [0.1500, 0.6751] |
| cross_session · 정규화 on | 0.4742 | **0.5090** | [0.3965, 0.6216] |

**정정 2 — T3의 상한 정의 (`within_subject` → `ceiling_nodrift`, 이번 절 본문 참조):**

원래 T3는 `within_subject`(같은 세션 안에서 블록만 나누는 분할)를 "도달 가능한
상한"으로 썼다. **이것은 계획 결함이었다** — `within_subject`는 세션 간 이동을
아예 겪지 않으므로 `cross_session`(leave-one-session-out)과 애초에 답하는 질문이
다르고, **드리프트가 전혀 없어도 도달 불가능**하다: `cross_session`(드리프트
0·정규화 off)=0.5743인데 `within_subject`(같은 조건)=0.8583이다. 원래 비율은
(a) 드리프트가 낸 손상과 (b) 두 CV 방식의 본질적 난이도 차이를 뒤섞어 재고
있었다. (b)까지 정규화 탓으로 돌리면 정규화가 완벽해도 영원히 실패하는 기준이
된다.

**새 상한은 `ceiling_nodrift`**(같은 분할기 `cross_session`·같은 시드, 드리프트
시그마만 0)다 — 측정 드리프트가 없었다면 실제로 도달 가능했을 성능.

| 조건 | pooled accuracy | fold CI |
|---|---|---|
| cross_session · off (실제 드리프트) | 0.4126 | [0.1500, 0.6751] |
| cross_session · on (실제 드리프트 + 정규화) | 0.5090 | [0.3965, 0.6216] |
| **cross_session · ceiling_nodrift**(드리프트 0, 정규화 off) | **0.5743** | [0.5452, 0.6033] |
| within_subject (맥락 — 상한 아님, cv_method 다름) | 0.8583 | [0.8139, 0.9033] |
| chance | 0.3333 | — |

**회복률 = (on − off) / (ceiling_nodrift − off) = (0.5090 − 0.4126) / (0.5743 − 0.4126)
= 0.0964 / 0.1617 = 0.596 → 요구 ≥ 0.5, PASS.**

드리프트가 낸 손상이 유의미한지 먼저 확인했다: `ceiling_nodrift − off = 0.1617`이
`off` 자신의 fold 수준 표준오차(`(fold_ci_high − fold_ci_low) / (2·t(0.975,2))`
= 0.525/8.606 = 0.061)보다 크다 — 드리프트가 실제로 신호를 흔들었다는 뜻이고,
그래야 "회복"이 의미를 갖는다.

**정정 3 — T4의 기준(`b_ref`) 정의 (Task 15, `session_clean.yaml`, seed 42):**

§8.2를 쓴 시점에는 `concentration_delta`가 뺄셈만 해서 `normalize=False`(원 단위)와
`normalize=True`(정규화 단위)가 같은 자로 잰 값이었다. **정정 1**(위)로 베이스라인
산포로도 나누게 되면서 이 전제가 깨졌다 — `normalize=True`의 결과 단위가 "베이스라인
산포 대비 배수"(무차원)로 바뀌어 `normalize=False`의 원 농도 단위와 더 이상 같지 않다.

실측으로 확인됐다: `b_ref`를 브리프 원안대로 `_practice_slope(session_clean.yaml,
normalize=False)`로 두면 -0.0358(원 단위)이 나오고, `b_hat`
(`_practice_slope(session_recovery.yaml, normalize=True)`)은 -2.5812(배수 단위)가
나와 **비율이 72.07로 발산한다.** 연습 효과가 커진 게 아니라, 세션 베이스라인
산포(σ≈0.014)가 작아 나눗셈이 값을 그만큼 확대했을 뿐이다 — 순수한 단위 불일치다.

**수정: `b_ref`도 `normalize=True`로 계산한다** (드리프트만 끄고 정규화 파이프라인은
`b_hat`과 동일하게 태운다). 이는 정정 2의 `within_subject → ceiling_nodrift`와 같은
원칙("같은 파이프라인, 드리프트만 다르다")을 단위 축에도 적용한 것이다.

| 기울기 | 조건 | 값 |
|---|---|---|
| `b_ref` | session_clean · 드리프트 off · **정규화 on** | -1.9951 |
| `b_hat` | session_recovery · 드리프트 on · 정규화 on | -2.5812 |

**보존율 = b_hat / b_ref = -2.5812 / -1.9951 = 1.294 → [0.5, 1.5] 안, PASS.**

**1을 넘는 것(과대 추정)의 원인 — 정정 (리뷰 2026-08-19가 이 절의 초판 설명을
반박했다).** 초판은 "베이스라인 16개 창에서 σ̂를 추정하는 잡음"을 원인으로 적었으나,
**분해 실측이 이를 반박한다.** `session_recovery.yaml`의 `within_session_rate`를
0으로 override한 채(다른 드리프트는 그대로) `b_hat`을 다시 계산하면 **보존율이
정확히 1.000000**이 나온다(세션별 평균값까지 `b_ref`와 완전히 같다). 즉:

- **곱셈 이득(①옵토드 재부착)과 가산 오프셋(②캡·임피던스)은 §6.2 정정 1이
  완전히 소거한다** — 이 성분만 있으면 보존율은 정확히 1이다. σ̂ 추정 잡음의
  기여는 **0**이다.
- **1.294의 29%p 초과분은 전부 세션 *내* 드리프트(③, `within_session_rate=0.30`)의
  잔여물이다.** 시작 베이스라인만 보는 정규화는 세션 내에서 서서히 밀리는
  드리프트를 원리적으로 못 잡는다(CLAUDE.md §3.8: ③은 정규화가 아니라 **플래그**
  대상으로 규정돼 있다) — 정규화가 지우지 못하는 것을 지우지 못했을 뿐이며,
  이는 §6.2 정정 1이 겨냥한 문제(①②)가 아니다.

**이것은 좋은 소식이다** — §6.2 정정 1이 겨냥한 대상(곱셈 이득)을 **정확히**
지운다는 직접 증거이기 때문이다. `concentration_delta`가 베이스라인 산포로
나누는 수정이 의도대로 작동한다.

여유의 크기를 결정하는 것도 매끄러운 잡음이 아니라 **24개 피험자-세션에 대한
거친 베르누이 배정**이다(`session.py`의 `within_big = u < within_session_fraction`
— 세션마다 "세션 내 드리프트가 크게 걸렸는지"를 동전 던지듯 결정한다). 시드를
바꿔 이 배정이 달라지면 보존율도 함께 흔들린다:

| 시드 | `b_ref` | `b_hat` | 보존율 |
|---|---|---|---|
| 42 | -1.9951 | -2.5812 | 1.294 |
| 0 | -3.6740 | -3.0957 | 0.843 |
| 1 | -3.6190 | -3.3728 | 0.932 |
| 7 | -3.1962 | -4.0703 | 1.274 |

네 값 모두 `[0.5, 1.5]` 안이지만 1.294·1.274는 상한에 20%p 남짓 여유만 있다 —
③을 더 크게 배정받는 시드(피험자-세션이 `within_session_fraction=0.33`보다 더
많이 "큰 드리프트" 쪽으로 몰리는 경우)에서는 상한을 넘을 수 있다. 이는 T4
자체의 결함이 아니라 §6.2 정규화가 구조적으로 다루지 않는 변동원(③)이 노출된
것이며, `drift_flag`(§3.8·§8.3)가 이런 세션을 걸러내는 것이 설계 의도다.

**결함 주입(§8.2 요구: 분모를 베이스라인 블록이 아니라 세션 전체의 산포로 바꾸는
것)도 재검증했다.** 브리프가 준 `_ZScoreBaseline.apply`는 이미 `apply()`에 넘어오는
인자(`_practice_slope`가 넘기는 `feats` 전체 — 베이스라인+과제 전 구간)의 표준편차로
나누므로 별도 재설계 없이 요구를 만족했다. `b_ref`를 정정 3대로 -1.9951로 고정하고
측정한 결과, `b_bad`(주입된 정규화기로 계산한 `b_hat`) = -0.00053, 보존율 = 0.000266
→ 하한(0.5)을 크게 밑돌아 **주입이 명확히 빨간불을 낸다.**

**정정 4 — Critical: `b_ref` 자체가 죽으면 비율이 잡음/잡음이 된다 (리뷰
2026-08-19, `T4_REF_SLOPE_MIN` 도입):** 정정 3은 `b_ref`·`b_hat` 둘 다 같은
정규화 파이프라인을 태우게 했다. 그런데 이는 곧 **정규화 결함이 양쪽 모두에서
연습 효과를 죽이면 비율이 무의미해질 수 있다는 뜻이기도 하다** — `b_hat`에만
결함을 주입하는 위 결함 주입 테스트는 이 경우를 시험하지 않는다.

리뷰가 실증했다: `b_ref`·`b_hat` 둘 다 `_ZScoreBaseline`(§8.2 결함 주입)으로
계산하면 `b_ref` 자신이 살아있는 값(1.995~3.674)에서 **200~7000배 작은** 죽은
값(0.0005~0.017)으로 무너진다. 이 상태에서 비율만 보면:

| 시드 | `b_ref`(죽음) | `b_hat`(죽음) | 비율 | 원래(가드 없는) 판정 |
|---|---|---|---|---|
| 42 | 0.002994 | -0.000530 | -0.177 | FAIL(부호가 우연히 갈려서) |
| 0 | 0.011514 | 0.015164 | **1.317** | **PASS(거짓)** |
| 1 | -0.017350 | -0.014613 | **0.842** | **PASS(거짓)** |

`abs(b_ref) > 1e-9` 가드는 죽은 값(0.0005~0.017)보다 6~7자릿수 낮아 전혀 못
막는다. **수정: `b_ref`의 절대 하한 `T4_REF_SLOPE_MIN = 0.5`를 비율 검사보다
먼저 검사한다** — 관측된 생존값(1.995~3.674)의 1/4, 관측된 죽은 값의 최댓값
(0.017)의 30배 이상으로 사전에 선언했다. `tests/evaluation/test_validation_
session.py::test_t4_injection_symmetric_kill_is_caught_by_ref_floor`가 이
경로를 시험한다 — 양쪽을 다 죽인 뒤 가드가 실제로 막는지 확인한다.

**컨트롤러의 예시 계산(회복률 ≈0.98)과 실측이 다른 이유를 밝힌다.** 컨트롤러가
제시한 예시는 필자가 사전에 보고한 "청정 cross_session" 수치(0.5112)를 근거로
계산됐는데, 그 수치는 **`normalize: true`(정규화 on) 상태에서 드리프트만 끈**
값이었다 — `ceiling_nodrift`의 정의(드리프트 0 **그리고** `normalize: false`)와
다르다. 실제로 코드에 구현한 `ceiling_nodrift`(드리프트 0, `normalize: false`)는
0.5743이며, 이 값으로 계산한 회복률은 0.596이다. `(on−chance)/(ceiling_nodrift
−chance)` 형태로 계산하면 0.729로, `(on−off)/(ceiling_nodrift−off)`와 값이
갈린다(off≠chance이므로 두 형태가 대수적으로 같을 이유가 없다) — 컨트롤러가 "두
형태가 일치한다"고 관찰한 것은 계산에 쓰인 `ceiling_nodrift`(0.5112, on 상태)가
우연히 만든 결과였다. 공식은 컨트롤러가 명시한 `(on−off)/(ceiling_nodrift−off)`
를 그대로 채택했다(§본문 지시).

**T3 결함 주입(타 세션 베이스라인)도 새 기준에서 재확인했다.** 최초 구현은
`SessionBaseline(reference=reference, kind=kind)`처럼 `scale`을 안 넘겨, 참조
(reference)를 타 세션 것으로 바꾸는 의도한 결함에 더해 §6.2 이득 보정까지
함께 꺼버리는 **두 번째 결함을 우연히 함께 주입**하고 있었다(리뷰에서 발견,
2026-08-19 정정). `scale=real.scale`(자기 세션의 산포는 유지)로 고쳐 참조만
타 세션으로 바뀌도록 격리했다: off=0.4126, foreign-on=0.3999,
ceiling_nodrift=0.5743 → 회복률 = **−0.078**(< 0.5, PASS) — 참조만 바뀌어도
여전히 압도적으로 빨간불이며, 결론은 그대로 유지되면서 주입이 "타 세션
베이스라인"이라는 이름에 맞는 특정성을 얻었다. 이전 기준(within_subject
상한)에서는 정상 케이스 자체가 이미 0.5 미만이라 주입 테스트의 판별력이
의심스러웠는데, 새 기준에서는 정상(0.596)과 주입(−0.078)이 뚜렷이 갈려
**주입 테스트가 실제로 뭔가를 증명하게 됐다.**

**임계를 절대 수치로 두지 않았다.** T2는 chance가 fold 수준 t-CI 안에 있는지로,
T3는 `ceiling_nodrift` 대비 회복률로 판정한다. 둘 다 그 실행 자신이 만드는
기준점이므로 사전에 숫자를 지어낼 필요가 없다. `T3_GAP_RECOVERY_MIN = 0.5`는
그대로 뒀다.

**실측 헤드룸은 얇다 — "여유 있게 넘는다"는 표현을 걷어내고 수치로 남긴다
(CLAUDE.md §5.4).**

- **accuracy 단위:** 통과선(회복률 0.5에 해당하는 `on` 정확도) = `off + 0.5·
  (ceiling_nodrift − off)` = 0.4126 + 0.5·0.1617 = **0.4934**. 실측 `on` =
  **0.5090**. 여유는 **0.0156**뿐이다. 그런데 `on`의 fold CI 폭
  (`fold_ci_high − fold_ci_low`)은 **0.2252** — 통과 여유(0.0156)의 **14배**다.
  fold 3개짜리 t-CI가 이렇게 넓다는 것은, 이 파일럿 규모에서 `on`의 점추정이
  운 좋게 통과선 위에 앉았을 뿐 안정적으로 그 위에 있다고 주장할 근거가
  약하다는 뜻이다.
- **도달 가능한 최대치:** 드리프트가 **전혀 없을 때도** `on`(정규화는 켠 채)이
  낼 수 있는 최선은 `on_nodrift` = 0.5112다 (이 값이 바로 컨트롤러 예시 계산에
  쓰인 그 수치이며, 드리프트가 없어도 정규화가 원본과 완전히 같은 값을 내지는
  않는다는 것을 보여준다 — 베이스라인 산포로 나누는 연산 자체가 스케일을
  바꾸기 때문이다). 이를 회복률로 환산하면 `(on_nodrift − off) / (ceiling_nodrift
  − off)` = **0.6102**가 **이 파이프라인·이 파일럿 규모에서 회복률이 원리적으로
  도달할 수 있는 최댓값**이다(드리프트를 완전히 없애도 1.0에 못 미친다).
  임계(0.5)와 이 최댓값(0.6102) 사이의 폭은 **0.1102뿐**이고, 실측 회복률
  0.5966은 그 최댓값의 **97.8%**(`0.5966/0.6102`)를 이미 쓰고 있다 — 개선의
  여지가 사실상 남아 있지 않은 지점에서 겨우 통과선을 넘었다는 뜻이다.
- **단일 시드 결과다.** 위 모든 수치는 `seed=42` 한 번의 실행이다. B1
  서브프로젝트 전체의 T3 합격 판정이 이 한 시드에 걸려 있으며, 다른 시드에서
  재현되는지는 확인하지 않았다. 시드를 바꿔 돌리면 통과·미달이 뒤집힐 수
  있다.

이 세 가지(0.0156의 얇은 accuracy 마진 vs 0.2252의 CI 폭, 97.8%까지 찬 회복률
헤드룸, 단일 시드)를 종합하면 **T3는 통과했지만 그 통과는 튼튼하지 않다.**
파일럿 규모(8명·3세션·EEG 250Hz)를 키우거나 여러 시드로 재현하기 전에는 이
PASS를 "정규화가 확실히 작동한다"는 강한 근거로 인용하지 않는다.

**브리프 원안 드리프트 시그마로는 T2가 통과하지 못했다.** `fnirs_gain_sigma=0.20`
등 원안 값으로는 cross_session·정규화-off pooled accuracy가 0.5532로, 심어둔
진짜 인지 효과(`effect_size=0.8`)가 드리프트를 압도해 chance로 무너지지 않았다.
`assignment: sampled`에서는 `session.py`의 `between_big`이 항상 `False`로
고정되어 `between_session_scale`(4.0)이 전혀 적용되지 않으므로, 실제로 드리프트
강도를 올리는 손잡이는 `fnirs_gain_sigma`·`fnirs_offset_sigma`·`eeg_gain_sigma`
뿐이었다. 이 셋을 8배로 올려(무작위 잡음인 `eeg_noise_sigma`는 그대로 두었다 —
정규화로 고칠 수 없는 잡음을 늘리는 것은 "드리프트 강화"가 아니다) off를 chance
근처로 무너뜨렸다. **정규화 정정(§6.2) 후에도, T3 상한 정정 후에도 시그마를
원안으로 되돌릴 수 없었다** — off는 정규화를 쓰지 않는 조건이라 두 정정 모두와
무관하고, 원안 시그마에서는 여전히 pooled 0.5532로 붕괴하지 않는다(재확인
완료). 8배 시그마를 그대로 유지한다.

**정정 5 — T5·T6 (Task 16, `session_quality.yaml`, seed 42, n_subjects=4·
n_sessions=4·`drift.assignment: fixed_2x2`):**

**T5(누수)는 3개 전부 PASS.** `check_normalization_source`가 베이스라인 창을
옵트인한 데이터셋(`include_baseline=True`, target=`accuracy`)에서 실제로
`LeakageError`를 던지고, 가드를 끄면(`check_normalization_source: False`)
실제로 통과해버리는 것도 확인했다 — 가드가 무엇을 막는지 결함 주입으로
증명됐다. `SessionBaseline.fit`의 서명(`start_baseline, kind`)도 §6.1대로다.

**T6(신뢰도 플래그)의 메인 판정(`test_t6_flags_only_the_sessions_with_
within_session_drift`)은 현재 구현에서 통과할 수 없다 — §6.3 정의와 무관하게
`compute_drift`가 fnirs 모달리티에서 근본적으로 신뢰할 수 없는 값을 낸다.
`xfail(strict=True)`로 표시해뒀다(테스트 파일 참조). 임계는 건드리지 않았다
(스펙 §8.4.1의 "임계는 실측 후 근거와 함께 고정" 원칙과, 브리프의 "§6.3
문제면 임계를 만지지 말고 보고" 지시를 함께 따랐다).

실측(4피험자 × 4세션, 2×2 고정 배치):

| 세션 | ①② 세션 간 | ③ 세션 내 | eeg 집계(4명) | fnirs 집계(4명) | 기대 플래그 |
|---|---|---|---|---|---|
| 0 | 작음 | 작음 | 0.1056–0.1374 | 2.76–32.80 | ✗ |
| 1 | 작음 | 큼 | 0.6446–0.6678 | 2.12–169.64 | ✓ |
| 2 | 큼 | 작음 (핵심 칸) | 0.1189–0.1329 | 1.59–168.48 | ✗ |
| 3 | 큼 | 큼 | 0.5836–0.6631 | 3.19–23.27 | ✓ |

**eeg는 완전히 분리된다** — 작은 군의 최댓값(0.1374)이 큰 군의 최솟값(0.5836)보다
작다. 임계 0.20은 이 분리 구간 [0.1374, 0.5836] 안에 있으므로 **eeg에 대해서는
이미 올바르게 배치돼 있다.** 조정할 필요도 근거도 없었다.

**fnirs는 within_big·between_big 어느 쪽과도 상관관계가 없다.** 세션1(within
큼) 최솟값 2.12이 세션2(within 작음, 핵심 칸) 최댓값 168.48보다 작다 — 즉
겹치는 구간이 없는 정도가 아니라 **순서 자체가 반대**라, 어떤 단일 임계값
`T`로도 "세션1 전원 플래그 AND 세션2 전원 비플래그"를 동시에 만족시킬 수 없다
(`T < 2.12`이면서 동시에 `T ≥ 168.48`이어야 하므로 모순). 드리프트를 전부
0으로 꺼도(`fnirs_gain_sigma=fnirs_offset_sigma=eeg_gain_sigma=eeg_noise_sigma
=within_session_rate=0`) fnirs 값은 여전히 3.4~174 범위에 머문다(세션·피험자와
무관) — 즉 이 값은 ①②③ 어느 드리프트 메커니즘과도 무관한 잡음이다.

**원인 진단.** `fnirs` 특징 벡터는 `[HbO 평균(48) | HbO 기울기(48)]`를 이어붙인
96차원이다(`src/datasets/features_minimal.py`). 베이스라인 창은 정의상 안정
상태라 "기울기"(창 내 선형 추세) 특징은 참값이 0 근처다. `compute_drift`의
상대 비율(§6.3: `||end−start|| / ||start||`)을 이 근사-영 특징에 적용하면
분모가 잡음 수준으로 작아 비율이 발산한다 — 채널별 분해로 확인: `hbo_slope`
집계가 `hbo_mean` 집계보다 일관되게 몇 배~수십 배 크다(예: sub-04 세션2:
mean_agg=3.48, slope_agg=333.49). `zero_atol`(1e-8)은 "정확히 0"만 걸러내는
수치적 하한이라 이 스케일의 잡음(평균 시작값 ~0.001~0.05대)을 전혀 걸러내지
못한다. 이는 세션 간 드리프트를 세션 내로 오독하는 것과는 다른, 더 근본적인
결함이다 — fnirs 값이 애초에 **어느 드리프트와도 무관한 잡음**이기 때문이다.

**Task 16 범위 밖이다.** 이 태스크의 파일 범위는 config·테스트뿐이다. 수정은
`compute_drift`(§6.3)가 모달리티별로 어떤 특징 부분집합에 상대 비율을
적용하는지 다시 설계하거나(예: `concentration_delta` 드리프트는 `hbo_mean`
서브셋에만 적용), 기울기류 특징에는 절대 임계 또는 다른 형태의 안정성 지표를
쓰는 후속 작업이 필요하다. 후속 작업 전까지 `SessionQuality.drift_flag`는
fnirs가 관여하는 한 신뢰할 수 없다 — §6.3이 "에포크 → 데이터셋 → 결과 →
대시보드까지 따라간다"고 규정한 값이므로, 대시보드에 fnirs 기반 플래그를
그대로 노출하면 안 된다.

**T6(0-임계 주입)은 PASS.** `drift_threshold_relative=0.0`으로 낮추면 모든
세션이 플래그된다 — 값의 정확성과 무관하게 "임계가 낮을수록 특이도가
무너진다"는 방향성만 확인하는 테스트라 fnirs 결함의 영향을 받지 않는다.

**정정 6 — compute_drift 분모 수정 (Task 16, 컨트롤러 판정).** 컨트롤러가
정정 5의 진단을 결함으로 확정하고 수정을 지시했다: `compute_drift`의 분모를
`|mean(start)|`에서 `std(start, ddof=1)`로 바꾼다. fnirs 특징이 `[HbO 평균 |
HbO 기울기]`를 이어붙이는데 "기울기"는 베이스라인(고정점 응시, 추세 없음)에서
**평균이 정당하게 0 근처**다 — 평균을 분모로 쓰면 이 채널들이 "수치적으로
0"과 구분되지 않아 발산한다. 산포를 쓰면 평균이 0이어도 정상적으로 다뤄지고,
§6.2 `concentration_delta`가 이미 같은 분모(베이스라인 산포)를 쓰므로 드리프트
지표가 정규화와 같은 단위("베이스라인 표준편차 배수")를 갖게 된다. 구현:
`src/preprocessing/baseline.py::compute_drift`.

재측정(session_quality.yaml, seed 42): eeg는 여전히 완전히 분리된다(작은 군
0.627538~0.788948, 큰 군 3.515019~4.222576) — 원래 결함(발산, 최대 174)은
해소되어 값이 물리적으로 말이 되는 범위(eeg 0.6~4.2, fnirs 0.48~5.0)로
줄었다. 임계를 eeg 분리 구간의 중간값 **2.15**로 재보정했다
(`session_quality.yaml` 주석 참조 — 단위가 바뀌어 옛 0.20은 더 이상 맞는
자리가 아니다).

**하지만 fnirs는 여전히 완전히는 분리되지 않는다 — 이번엔 종류가 다르다.**
세션0 sub-04의 fnirs=4.246897 하나가 세션1 sub-02의 eeg=4.222576보다 커서,
"세션1 전원 플래그 AND 세션0·2 전원 비플래그"를 만족하는 임계 구간
`[4.222576, 4.246897)`이 공집합이다(하한이 상한보다 크다). 채널 분해로
확인: 이 값은 슬로프 특징 하나가 아니라 HbO 평균·슬로프 둘 다에서 크다
(mean_agg=5.51, slope_agg=2.99) — 근사-영 분모로 인한 구조적 발산이 아니라
`n_subjects=4`의 작은 표본에서 나온 피험자 간 변동(`subject_variance=0.5`)
으로 보인다. **T6 메인 테스트는 `xfail(strict=True)`로 남긴다** — 원인이
"compute_drift가 §6.3을 잘못 구현했다"에서 "표본이 작아 fnirs 특이도가 아직
완전하지 않다"로 바뀌었을 뿐, 여전히 어떤 단일 임계로도 2×2를 채우지
못한다는 사실 자체는 그대로다. 상세:
`.superpowers/sdd/2026-08-19-session-baseline/task-16-report.md`.

`null.yaml`(assignment: sampled, 옛 threshold 0.20 그대로)로 재확인:
`n_sessions_flagged`는 여전히 **36/36**이다 — eeg 범위(0.264~4.521)·fnirs
범위(0.188~0.327)가 둘 다 0.20보다 크므로, 옛 threshold는 이제 모든
`drift_threshold_relative: 0.20` config에서 단위 불일치로 어긋나 있다는
뜻이다. `null.yaml` 자체의 임계는 Task 16 범위 밖이라 고치지 않았다 — 후속
작업으로 남긴다.

**정정 7 — T6 판정을 완전 분리에서 플래그 비율로, 임계를 프로젝트 전체에
일괄 반영 (컨트롤러 판정 2회차).** 정정 6의 "간격 0.024"를 컨트롤러가
재검토해 **판정 기준 자체가 과했다**고 결론지었다 — 브리프 원안이 요구한
"핵심 음성 칸의 *모든* 피험자가 양성 칸의 *모든* 피험자보다 낮을 것"은
`drift_flag`가 (피험자, 세션)마다 붙고 피험자 간 드리프트 크기가 다르다는
사실보다 엄격한 요구였다. n을 아무리 키워도 분포 꼬리에서 실패할 수 있다.
§8.3이 실제로 묻는 것은 민감도·특이도이므로, 판정을 **칸별 플래그 비율**로
바꿨다: 핵심 음성 칸(세션0·2)은 비율 ≤ `T6_NEGATIVE_FLAG_RATE_MAX`(0.25),
양성 칸(세션1·3)은 비율 ≥ `T6_POSITIVE_FLAG_RATE_MIN`(0.75) — 3:1 변별을
요구하는 사전 선언이다.

`session_quality.yaml`의 `n_subjects`를 4 → 8로 올렸다(비율이 n=4에서는
0/0.25/0.5/0.75/1.0 다섯 값만 가능해 추정이 거칠었다). 드리프트 시그마는
건드리지 않았다 — 문제를 숨기지 않기 위함이다.

재측정(seed 42, 8피험자×4세션, 임계 2.15):

| 세션 | 플래그 비율 | 기준 | 판정 |
|---|---|---|---|
| 0(①②·③ 작음) | 0.250 | ≤ 0.25 | PASS(경계에서) |
| 1(①② 작음·③ 큼) | 1.000 | ≥ 0.75 | PASS |
| 2(핵심 음성 칸, ①② 큼·③ 작음) | 0.125 | ≤ 0.25 | PASS |
| 3(①②·③ 큼) | 1.000 | ≥ 0.75 | PASS |

**T6 메인 테스트에서 `xfail`을 제거했다** — 이 기준으로 정상 통과한다.

**`drift_threshold_relative: 0.20`을 쓰던 나머지 config(`smoke`·`null`·
`pilot`·`session_recovery`·`session_clean`)도 전부 `2.15`로 일괄 갱신했다**
— 드리프트 지표가 스케일 자유이므로 프로젝트 단일 값이 맞다는 컨트롤러
판단에 따른 것이다. `null.yaml`로 재확인: `n_sessions_flagged`가
**36/36 → 12/36(33.3%)**로 내려왔다 — 더 이상 포화 상태가 아니다. eeg
범위(0.264~4.521)는 임계(2.15) 위아래로 걸쳐 있고 fnirs 범위
(0.188~0.327)는 전부 임계 아래라, 남은 플래그는 전부 eeg가 낸 것이다(옛
브리프 시그마·`assignment: sampled`에서 우연히 큰 이득을 뽑은 세션들로
보인다 — 컨트롤러가 예상한 "정상 범위로 내려온" 경우에 해당한다).

**하지 않은 것.** `n_subjects`·임계 외 다른 config 값(드리프트 시그마 등)은
만지지 않았다. 지시대로 A+D의 느린 검증 파일(`test_validation_leakage.py`·
`test_validation_subject_variance.py`)도 건드리지 않았다.

**정정 8 — 정정 6·7의 원인 진단이 틀렸다. 판정 B(비율 판정)를 되돌린다
(컨트롤러 3회차, 리뷰 반영).** 정정 6·7은 잔여 오탐(세션0 sub-04의
fnirs=4.246897)의 원인을 **"`n_subjects=4`의 작은 표본에서 나온 피험자 간
변동(`subject_variance`)"**으로 적었다. **틀렸다.** 리뷰어가
`baseline_duration_s`(20 vs 60)를 축으로 세 시드(42·7·2026)에서 직접
측정해 반증했다:

| `baseline_duration_s` | seed | s0 | s1 | s2 | s3 | 판정 |
|---|---|---|---|---|---|---|
| 20 | 42 | 0.250 | 1.000 | 0.125 | 1.000 | 완전 분리 실패 |
| 20 | 7 | 0.375 | 1.000 | 0.250 | 1.000 | 완전 분리 실패 |
| 20 | 2026 | 0.500 | 1.000 | 0.375 | 1.000 | 완전 분리 실패 |
| 60 | 42·7·2026 | 0.000 | 1.000 | 0.000 | 1.000 | **완전 분리** |

세션0·2의 오탐 비율이 시드마다 0.125~0.500으로 흔들린다는 것 자체가
"소표본 피험자 변동"으로는 설명되지 않는다(표본 크기·`subject_variance`는
시드와 무관하게 고정인데 결과가 시드마다 다르다는 것은 **표집(RNG) 자체가
아니라 추정 절차의 불안정성**을 가리킨다). **진짜 원인은 베이스라인 창
수다.** `baseline_duration_s=20`은 5초 창·1초 스텝(80% 오버랩)에서 창을
약 16개만 준다. **정정 6이 §6.3 분모를 `|mean(start)|`에서
`std(start, ddof=1)`로 바꾼 것 자체는 옳았다**(구조적 발산은 막았다 —
116배 역전이 0.024 간격으로 좁혀진 것이 그 증거) — **그러나 그 수정에는
대가가 있다.** 표본 표준편차 추정치는 창이 적을수록 분산이 크고(자유도
`n-1`이 작을수록 표본분산의 표집분포가 넓어진다), fnirs가 48채널이라 그
불안정한 추정치를 그대로 받아 채널마다 다른 방향으로 흔들리며 세션0·2
(핵심 음성 칸 포함)에 간헐적 오탐을 만든다. `baseline_duration_s=60`은
같은 창·스텝에서 약 56개 창을 주어 SD 추정이 안정되고, 세 시드 전부
완전 분리로 돌아온다(위 표) — 이는 `null.yaml`·`pilot.yaml`이 이미
60이었다는 사실과도 들어맞는다(그 config들은 애초에 이 문제를 겪지
않았을 것이다).

**함의: 베이스라인 길이가 드리프트 지표의 신뢰도를 결정한다.** 이는
시뮬레이터 config뿐 아니라 **실장비 프로토콜 설계에 직접 영향을 준다**
— CLAUDE.md §2.4·§3.8이 규정하는 세션 시작·종료 베이스라인 측정 시간을
짧게 잡으면(예: 실험 시간 절약을 위해 20초로), §6.3의 신뢰도 플래그
자체가 신뢰할 수 없어진다. 최소 베이스라인 길이(예: 창 수 하한)를
프로토콜 설계 시점에 정해야 한다 — 이번 관측(56개 창에서 안정, 16개
창에서 불안정)이 그 하한을 정할 때의 1차 근거가 된다.

**되돌린 것.**

1. `session_quality.yaml`의 `baseline_duration_s`를 20 → 60. (다른 T5·T6
   전용이 아닌 config들은 원래 20 또는 60이었고, 이번 정정은 T6 config
   하나에만 적용한다 — `session_recovery`·`session_clean`은 T2·T3가 이미
   통과 중이므로 건드리지 않는다.)
2. T6 메인 테스트를 **정정 7 이전(브리프 원안)의 완전 분리 기준**으로
   되돌렸다 — `not any(flagged[0])` / `all(flagged[1])` /
   `not any(flagged[2])` / `all(flagged[3])`. `T6_NEGATIVE_FLAG_RATE_MAX`·
   `T6_POSITIVE_FLAG_RATE_MIN`(정정 7이 도입한 비율 상수)은 삭제했다.
   실패 메시지에는 네 칸의 플래그 목록·실측 드리프트 값을 계속 출력한다
   (진단용).
3. `n_subjects=8`은 **유지한다** — 되돌릴 이유가 없고, 표본이 많을수록
   완전 분리 요구가 더 엄격한 시험이 된다.
4. `test_t6_injection_zero_threshold_destroys_specificity`(임계를 0으로
   낮추는 주입)를 폐기했다 — 드리프트가 정확히 0이 아닌 한 무조건
   플래그되므로 거의 항진명제였고, "임계가 config에서 읽힌다"만 검증했다.
   대신 `compute_drift`가 종료 베이스라인을 못 보게 만드는(시작 베이스라인
   자기 자신과 비교) 진짜 결함 주입을 추가했다 — 양성 칸(세션1·3)이
   100%에서 0%로 무너지는 것을 확인한다.

**재측정 (session_quality.yaml, `baseline_duration_s=60`, `n_subjects=8`,
seed 42):** eeg·fnirs 둘 다 완전히 분리된다. 세션0·2(핵심 칸 포함)는
eeg·fnirs 어느 모달리티로도 전원 비플래그, 세션1·3은 전원 플래그. **정정
7의 "T6 승인기준이 처음으로 정상 PASS 상태에 도달했다"는 서술은 유지되지만
근거가 바뀐다** — 비율 기준에서는 변별력이 사실상 eeg 혼자 냈고(fnirs는
세션0 sub-04 하나 때문에 미달), 이번엔 **eeg·fnirs 둘 다** 완전 분리에
기여한다(정정 6이 밝힌 대로 fnirs 자체는 물리적으로 말이 되는 범위로
돌아왔고, 그 값이 실제로 세션 내 드리프트와 상관되는 것까지 이번에
확인됐다).

**판정 A(§6.3 분모를 SD로)는 유지, 판정 B(T6 판정을 비율로 완화)는
철회한다.** 판정 A가 옳았다는 것은 정정 6의 116배 역전 해소와, 이번 정정의
"베이스라인만 늘리면 완전 분리로 돌아온다"는 사실 둘 다로 뒷받침된다.
판정 B는 "고칠 수 있는 측정 아티팩트(짧은 베이스라인)를 판정 기준 완화로
흡수"한 것이었다 — 되돌린다.

### 9.1 P1을 함께 고친다

A+D 최종 리뷰에서 남긴 P1: `runner.py`가 오버라이드를 `load_config` **뒤에**
병합해서 스키마 검증을 우회한다. 오타 난 키가 조용히 통과하고, config 해시만
바뀌고, 아무 손잡이도 돌리지 않는다.

어차피 `runner.py`를 건드리고, **B1은 config 키를 여럿 추가하므로 위험이 오히려
커진 상태다.** 병합 후 `_check_node(cfg, SCHEMA, "")`를 다시 호출한다.

## 10. 새 config 키

`src/common/config.py`의 스키마는 **적힌 키를 전부 필수**로 취급하므로, 기존
config 3개(`smoke`/`null`/`pilot`)를 모두 갱신해야 한다.

```yaml
simulation:
  n_sessions: 3
  task:
    baseline_duration_s: 60
  practice:
    rate: 0.15                    # 세션당 인지부하 감소 비율 (④)
  drift:
    fnirs_gain_sigma: 0.20        # ① LogNormal sigma
    fnirs_offset_sigma: 0.10      # ①
    eeg_gain_sigma: 0.15          # ②
    eeg_noise_sigma: 0.15         # ②
    within_session_rate: 0.30     # ③ 큰 드리프트 세션의 rate
    within_session_fraction: 0.33 # ③ 큰 드리프트 세션의 비율
    assignment: sampled           # sampled | fixed_2x2 (T6 전용, §8.3)
    between_session_scale: 4.0    # ①② 세션 간 드리프트 배율. fixed_2x2에서만 적용됨(§12.9). 스키마 필수 키

preprocessing:
  baseline:
    drift_threshold_relative: 2.15  # 시작 베이스라인 **표준편차(SD) 배수**. 전 config 공통값(§8.4.1 "정정 7")

evaluation:
  guards:
    check_session_overlap: true
    check_normalization_source: true
```

**2026-08-19 정정 (최종 리뷰) — 위 두 값은 초판 이후 실측으로 확정됐다.**
`drift_threshold_relative`는 초판 `0.20`("시작 베이스라인 크기 대비 비율")에서
`2.15`로 바뀌었다 — §6.3 정정으로 `compute_drift`의 분모가 크기(`|mean(start)|`)
에서 산포(`std(start, ddof=1)`)로 바뀌며 단위 자체가 "베이스라인 SD 배수"로
바뀌었기 때문이다(옛 0.20은 새 단위에서 아무 의미가 없다). `between_session_scale`
은 초판 예시에 누락돼 있었으나 `src/common/config.py` 스키마가 이를 필수 키로
요구한다 — 누락하면 config 로드가 실패한다.

수치는 **초기값이며 파일럿 보정 대상**이다. 특히 `drift_threshold_relative`는
§8.4에 따라 측정 후 확정했다(현재 `2.15`, 실측 근거는 §8.4.1 "정정 6·7·8").

임계를 절대값이 아니라 **시작 베이스라인 SD 배수**로 두는 이유: 절대값은
모달리티·단위·진입 수준마다 스케일이 달라 하나의 숫자로 표현할 수 없다. 이
배수는 스케일 자유이므로 B2·B3가 들어와도 의미가 유지된다.

## 12. 이 스펙이 증명하지 않는 것

A+D에서 T3가 *피험자 혼입* 부풀림은 증명했으나 계획서가 최대 리스크로 지목한
*창 오버랩* 부풀림은 증명하지 않았다는 사실을 뒤늦게 발견했다. 같은 일을 반복하지
않기 위해 **한계를 미리 적는다.**

1. **드리프트 모델이 실제 옵토드 재부착과 닮았다는 것을 증명하지 않는다.**
   구조(LogNormal 곱셈 이득)를 우리가 정했다. 실장비 데이터로만 검증 가능하다.
   B1이 증명하는 것은 "**우리가 심은 형태의** 드리프트를 정규화가 지운다"이다.

2. **연습 효과의 실제 형태를 증명하지 않는다.** 기하 감쇠를 가정했다. 실제는
   천장 효과나 다른 곡선일 수 있다. T4가 증명하는 것은 "정규화가 세션 간 상태
   변화를 **원리적으로** 보존한다"이지 "이 크기의 학습을 검출한다"가 아니다.

3. **실제 전처리 체인과의 상호작용을 증명하지 않는다.** B1은 농도 진입만 안다.
   mBLL·SCI·ASR이 정규화와 어떻게 상호작용하는지는 B2·B3의 몫이다.

4. **세션 3회에서 얻은 결론이 더 많은 세션으로 확장되는지 증명하지 않는다.**

5. **⑤ 일간 변동을 다루지 않는다.** 의도적 제외다(§4). 실데이터 확보 후 KSS·수면
   시간을 공변량으로 E에서 다룬다.

6. **B1의 모든 정확도 수치는 융합 모델의 성능과 무관하다.** 특징은 A+D의 임시
   추출기(`features_minimal`), 분류기는 더미 로지스틱 회귀다. T3의 "회복 수준"은
   **정규화가 작동한다는 증거이지 이 과제가 달성 가능한 성능의 추정치가 아니다.**
   계획서 목표치(이진 90% / 다분류 85%)와 나란히 놓아서는 안 된다.
   B1 결과를 인용할 때는 특징·모델이 임시라는 사실을 함께 적는다.

7. **세션 간(cross-session) 일반화와 세션 내(within-session) 일반화의 본질적
   격차는 정규화가 좁히는 대상이 아니다.** `cross_session`(leave-one-session-out)
   은 학습에 다른 세션만 쓰므로 그 세션의 채널 이득을 본 적이 없는 상태로
   평가되고, `within_subject`는 같은 세션 안에서 블록만 나누므로 채널 이득을
   이미 본 채로 평가된다 — 애초에 답하는 질문이 다르다. Task 14의 T3 재설계
   과정에서 실측으로 확인됐다: 드리프트를 완전히 꺼도(`normalize: false`)
   `cross_session`(0.5743)이 `within_subject`(0.8583)에 크게 못 미친다. 이
   격차는 정규화의 대상이 아니라 두 CV 방식의 구조적 성질이므로, "정규화가
   이 격차까지 메워야 한다"는 기준(예: 원래의 T3 상한 설계)을 다시 쓰지 않는다.
   상세: §8.2·§8.4.1.

8. **T2·T3(cross_session 붕괴·회복)는 `session_recovery.yaml`의 드리프트 시그마
   조정에 민감하다.** 브리프 원안 시그마(1배)로는 T2가 요구하는 붕괴가 재현되지
   않았다 — 정규화 off에서도 pooled accuracy=0.5532로 chance(0.3333)를 넘었다
   (`effect_size=0.8`의 진짜 인지 효과가 드리프트를 압도). fnirs_gain_sigma·
   fnirs_offset_sigma·eeg_gain_sigma를 8배로 올려서야 붕괴가 재현됐다(off
   pooled=0.4126). **T3가 증명하는 것은 "이 정도 크기(8배 시그마)의 드리프트에
   대해서는 정규화가 회복시킨다"이지, 임의 크기의 드리프트에 대한 일반 증명이
   아니다.** 시그마를 더 키우면 회복률(현재 0.5966, 여유 얇음)이 임계 0.5 아래로
   떨어질 가능성을 배제하지 않는다.

9. **T6의 2×2 배치는 `between_session_scale=4.0`에 실제로 의존한다.**
   `src/simulation/session.py`의 `plan_sessions`는 `assignment: fixed_2x2`
   (T6 전용 `session_quality.yaml`이 씀)일 때만 `between_session_scale`을
   적용해 ①② 세션 간 드리프트를 4배로 키운다 — `assignment: sampled`
   (T2·T3가 씀)에서는 `between_big`이 항상 `False`로 고정되어 이 파라미터가
   **아예 적용되지 않는다**(§8.4.1 정정 참조). 즉 T2·T3의 결과는
   `between_session_scale`과 무관하지만, T6의 "①②가 커도 ③이 작으면 플래그
   안 됨" 판정은 `between_session_scale=4.0`이 실제로 ①②를 키워준다는 전제
   위에 있다. 이 값을 바꾸면 T6의 2×2 대비가 약해질 수 있다.

10. **T2·T3·T4가 쓰는 `session_recovery.yaml`·`session_clean.yaml`은 여전히
    `baseline_duration_s=20`(베이스라인 창 ~16개)이다.** T6에서 같은 창 수가
    §6.3 드리프트 지표(SD 분모)의 표집분산을 불안정하게 만드는 것을 확인했고
    (§8.4.1 "정정 8"), 60초(~56개 창)로 늘리면 안정화됐다. T2·T3·T4는 이미
    통과 중이라는 이유로 `baseline_duration_s`를 건드리지 않았다.

    **2026-08-19 최종 리뷰에서 이 항목을 실측했다 (더 이상 미확인이 아니다).**
    `session_recovery.yaml`을 `baseline_duration_s`만 20→60으로 바꿔 seed 42로
    재실행한 결과:

    | | baseline=20s(현재 출하) | baseline=60s |
    |---|---|---|
    | T2 붕괴(off pooled) | 0.4126, fold_ci [0.1500, 0.6751] → chance 포함 → **PASS** | 0.4921, fold_ci [0.3947, 0.5894] → chance(0.3333) 밖 → **FAIL** |
    | T3 회복률 | off .4126 / on .5090 / ceiling .5743 → **0.5966 PASS** | off .4921 / on .5326 / ceiling .5833 → **0.4444 FAIL** |
    | T4 보존율 | b_ref −1.9951 / b_hat −2.5812 → **1.2938 PASS** | b_ref −2.2224 / b_hat −2.0758 → **0.9340 PASS**(1에 더 가까움) |

    그리고 드리프트를 전부 0으로 끈 `session_clean.yaml`이 20초에서 24개 세션 중
    3개를 `drift_flag`로 오탐한다(fnirs 집계 최대 3.750 > 임계 2.15) — 60초에서는
    0/24다.

    **결론: T2·T3는 `baseline_duration_s=20`에서만 PASS하고, 이 브랜치가 T6에서
    (§8.4.1 "정정 8") 신뢰할 수 있다고 결론지은 60초에서는 FAIL한다.** 이 브랜치는
    같은 σ̂(베이스라인 산포 추정치)를 `compute_drift`의 분모이자 `SessionBaseline.fit`
    의 `scale`로 함께 쓴다 — T6이 "20초는 σ̂ 추정을 불안정하게 만든다"고 결론짓고
    `session_quality.yaml`만 60초로 올린 시점부터, T2·T3·T4도 같은 불안정한 σ̂ 위에
    서 있다는 뜻이 됐다. 즉 **브랜치는 내부적으로 어긋난 상태로 병합된다.**

    **교란요인 (분리되지 않음).** 베이스라인을 20→60초로 늘리면 세션 총 길이가
    220s→300s가 되고, 세션 내 드리프트 램프 중 **과제 블록이 겪는 구간**의 비중이
    `rate·180/220` → `rate·180/300`으로 줄어든다 — 실제 드리프트 노출 자체가
    약해지므로 T2의 "붕괴" 조건이 덜 성립한다. **σ̂ 불안정성과 이 노출 감소는 이
    측정만으로 분리되지 않는다** — 위 표의 FAIL이 순전히 σ̂ 불안정성 때문인지,
    노출 감소 때문인지, 둘의 조합인지는 별도 실험(예: 세션 길이는 300s로 고정한 채
    베이스라인만 60초로 늘리고 과제 블록을 줄이지 않는 설계)이 있어야 갈릴 수 있다.

    **결정됨 (2026-08-20, 사용자): 20초를 유지한다.** 시그마 재보정도, 노출 감소를
    통제한 재실험도 하지 않는다. `session_recovery.yaml`·`session_clean.yaml`은
    `baseline_duration_s=20`으로 출하된다.

    **따라서 이 스펙이 증명하지 않는 것이 하나 늘어난다:** T2·T3의 PASS는 T6가
    "드리프트 지표를 신뢰하려면 필요하다"고 결론지은 것보다 **짧은 베이스라인
    위의 결과**다. 같은 σ̂가 `compute_drift`의 분모이자 §6.2 정규화의 `scale`이므로,
    T2·T3의 정규화는 T6가 요구하는 것보다 잡음 많은 σ̂ 위에서 돈다. **미결이라서가
    아니라 선택해서 이 상태이며**, T2·T3 수치를 인용할 때 이 한정을 함께 옮긴다.

    T3의 회복률(여유 0.0156)·T4의 보존율(여유 20%p)이 이미 얇은 여유로 PASS한
    상태였다는 점도 위 결과와 함께 읽는다. 상세: `run_logging.md` Task 17 갱신분.

이 한계들은 결과 보고 시 함께 기재한다(CLAUDE.md §5.4 성능 보고의 정직성).
